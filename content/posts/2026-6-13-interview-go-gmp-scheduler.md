### 前情提要

Go 能轻松撑起百万级并发，靠的不是魔法，而是一套精心设计的用户态调度器——GMP 模型。面试中聊到 Go 并发，GMP 几乎是绕不过去的坎。这篇笔记把 GMP 的核心知识整理清楚，方便面试时有条理地讲出来。

### 问题

面试官通常会这样问：

- "请介绍一下 Go 的 GMP 调度模型"
- "Goroutine 是怎么被调度到系统线程上执行的"
- "Go 的调度器和 Java/OS 的线程调度有什么区别"

考察的核心是：你是否理解 Go 运行时如何在用户态管理成千上万的轻量级协程，以及当阻塞、空闲、系统调用等场景发生时调度器如何应对。

### 回答

GMP 是 Go 调度器的三个核心角色：

**G — Goroutine（协程）**

每个 `go func()` 都会创建一个 G。G 里装着自己的栈空间、指令指针、运行状态。初始栈只有 2KB，可以按需动态增长。G 不是直接跑在 CPU 上的，它需要被调度到 M 上才能执行。

**M — Machine（操作系统线程）**

M 对应一个真实的 OS 线程。Go 运行时负责创建和管理 M，M 的数量可以远大于 P。M 本身不决定跑哪个 G，它听 P 的安排。

**P — Processor（逻辑处理器）**

P 是调度的核心枢纽。每个 P 维护一个本地 G 队列（Local Run Queue），P 的数量默认等于 CPU 核心数（由 `GOMAXPROCS` 控制）。P 决定了 M 接下来执行哪个 G。

三者的关系可以这样理解：P 是"工头"，M 是"工人"，G 是"任务单"。工头手里攥着一沓任务单，安排工人一个一个干。

**调度流程（找活干）**

当一个 M 需要找下一个 G 来执行时，查找顺序是：

```
1. P 的本地队列 → 最快，无锁
2. 全局队列     → 本地队列空了才去拿，需要加锁
3. 偷其他 P     → Work Stealing，从别的 P 本地队列偷一半过来
4. 网络轮询     → 检查有没有就绪的网络 I/O 事件（netpoller）
```

用伪代码表示就是：

```go
func findRunnableG() *G {
    if g := localQueue.pop(); g != nil { return g }     // 本地队列
    if g := globalQueue.pop(); g != nil { return g }    // 全局队列
    if g := stealFromOtherP(); g != nil { return g }    // 偷取
    if g := pollNetwork(); g != nil { return g }        // 网络轮询
    return nil                                          // 真没活了，休眠
}
```

**Handoff 机制（系统调用阻塞）**

这是面试高频追问点。当一个 G 进入阻塞式系统调用（比如文件读写），M 会和 P 解绑，P 转而去绑定一个空闲的 M（或创建新 M）继续干活。等系统调用返回后，原来的 M 再尝试重新获取 P。

```
阻塞前：  P0 ← M0（执行 G1）  →  G1 进入系统调用
阻塞时：  P0 ← M1（接手干活）  ，M0 带着 G1 阻塞
返回后：  M0 尝试获取 P，拿到就继续；拿不到就把 G 放回队列，M0 休眠
```

对于非阻塞的系统调用（比如 channel 操作、带超时的网络 I/O），Go 用 netpoller 异步处理，M 不会真的阻塞，可以直接去跑别的 G。

**调度发生的时机**

- `go func()` 创建新 G
- G 阻塞（channel、锁、系统调用）
- G 主动让出 `runtime.Gosched()`
- G 执行完毕，函数返回
- GC STW（Stop The World）暂停所有 G

### 分析

**为什么这么设计？**

GMP 的核心思路是把"调度"从内核搬到用户态。OS 线程的创建和上下文切换开销很大（涉及内核态切换、寄存器保存等），而 Goroutine 的切换完全在用户态完成，代价极低。P 的引入是关键——它把"哪些 G 可以跑"这个决策和 OS 线程解耦了，让调度器可以在用户态做最优分配。

Work Stealing 机制保证了负载均衡：不会一个 P 忙死、另一个 P 闲死。本地队列优先的设计减少了锁竞争——只有访问全局队列时才需要加锁，日常调度基本都是无锁的。

**和其他语言的对比**

| 维度 | Go (GMP) | Java (线程池) | Erlang (Actor) |
|------|----------|--------------|----------------|
| 调度单位 | Goroutine (~2KB) | OS Thread (~1MB) | Process (~300B) |
| 调度位置 | 用户态 | 内核态 | 用户态（BEAM VM） |
| 抢占方式 | 协作式 + 信号抢占 | 内核时间片 | 归约计数抢占 |
| 并发量级 | 百万级 | 千~万级 | 百万级 |

Java 的线程模型直接依赖 OS 调度，线程数多了上下文切换成本爆炸。Erlang 的 BEAM 虚拟机和 Go 思路相似，都是用户态调度，但 Erlang 用归约计数实现真正的抢占式调度，Go 在 1.14 之前是纯协作式的。

### 知识点总结

- **G（Goroutine）**：轻量级协程，2KB 初始栈，用户态调度
- **M（Machine）**：OS 线程，执行 G 的载体，数量可大于 P
- **P（Processor）**：逻辑处理器，持有本地 G 队列，数量 = GOMAXPROCS
- **调度顺序**：本地队列 → 全局队列 → Work Stealing → netpoller
- **Handoff**：系统调用阻塞时 P 与 M 解绑，保证其他 G 不受影响
- **触发时机**：创建、阻塞、让出、完成、GC

### 相关知识扩展

**Work Stealing 细节**

偷取时会从目标 P 的本地队列中拿走一半的任务到自己的队列里。为什么是一半？因为"刚好够用"——既减少偷取次数（不用频繁偷），又避免偷太多导致目标 P 自己没活干。Go 的实现中，本地队列是一个无锁的环形缓冲区（ring buffer），容量 256，偷取操作是原子的。

**Goroutine 抢占式调度**

Go 1.14 开始引入基于信号的抢占式调度。在此之前，如果一个 G 里有死循环，整个 P 绑定的 M 都会被卡住。1.14 之后，调度器会通过 `SIGURG` 信号中断长时间运行的 G，让它让出 CPU。这让 Go 的调度行为更接近操作系统的抢占式调度，但实现仍在用户态。

**GOMAXPROCS 调优**

`GOMAXPROCS` 默认等于 CPU 核心数，在大多数场景下不需要改。但在容器环境中（Docker/K8s），Go 运行时早期无法感知 cgroup 的 CPU limit，可能拿到的是宿主机的核心数而非容器分配的核心数，导致 P 过多、上下文切换增加。可以通过 `uber-go/automaxprocs` 库自动修正。在 CPU 密集型场景下，有时适当降低 GOMAXPROCS 反而能减少调度开销、提升吞吐。

### 学习路线与建议

1. **先理解概念**：搞清楚 G、M、P 三者各自是什么，不要死记
2. **画调度图**：自己手动画一遍 GMP 的调度流程，特别是 handoff 场景
3. **读 runtime 源码**：`runtime/proc.go` 中的 `schedule()` 函数是调度器核心入口
4. **做实验**：用 `GODEBUG=schedtrace=1000` 环境变量观察调度器行为
5. **面试表达**：按"G 是什么 → M 是什么 → P 是什么 → 怎么调度 → 阻塞怎么办"的顺序讲，条理清晰

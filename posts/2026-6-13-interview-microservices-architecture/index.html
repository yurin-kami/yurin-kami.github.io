面试笔记：微服务和单体架构怎么选

2026-06-13 微服务架构设计面试八股文

前情提要

最近准备二面，发现架构设计类问题几乎必问。之前整理的八股文里微服务部分比较零散，这次把单体、微服务、模块化单体三种架构的对比，以及服务治理的核心概念串一遍，算是给自己做一次系统性的复习。

问题：微服务到底解决了什么问题？

面试官的经典问法是「微服务架构的优缺点」和「什么时候该用微服务」。这个问题看起来简单，但如果没有实际踩过坑，很容易答成教科书式的罗列。我觉得更好的回答方式是从痛点出发：单体架构在项目规模增长之后会遇到什么问题，微服务又是怎么解决这些问题的。

回答

单体 vs 微服务 vs 模块化单体

单体架构（Monolith） 是最直觉的方式：所有功能模块跑在同一个进程里，共享同一个数据库。优点是开发简单、调试方便、部署也快，一个二进制文件丢上去就跑。缺点也很明显——代码膨胀之后编译变慢，模块之间耦合严重，改一行代码就得全量部署，某个模块的流量高峰也得整体扩容。

微服务架构 把系统拆成多个独立部署的服务，每个服务有自己的数据库和技术栈。核心优势：

  • 独立部署：一个服务发版不影响其他服务
  • 技术栈灵活：Go 写高性能网关，Python 做数据分析，各取所需
  • 按需扩展：热点服务单独水平扩容，不浪费资源
  • 故障隔离：订单服务挂了，用户服务还能正常响应
  • 团队自治：每个小团队全权负责自己的服务

代价是复杂度飙升——分布式事务、网络延迟、运维成本、链路追踪，每一个都是硬骨头。

模块化单体（Modular Monolith） 是两者的折中：代码还在一个仓库里，但按业务域严格划分模块，模块之间通过接口通信，不能直接访问对方的数据库表。部署时是一个整体，但逻辑上已经具备了微服务的边界感。对于大多数中小团队，这其实是更务实的选择。

微服务拆分原则

拆微服务最怕的是「拆得太细」或者「拆得不对」。几条核心原则：

  1. 单一职责：每个服务只做一件事，但「一件事」的粒度要靠业务判断，不是越细越好
  2. 高内聚低耦合：服务内部功能紧密相关，服务之间尽量通过事件或接口通信
  3. 按业务领域拆分（DDD）：用限界上下文（Bounded Context）来划定服务边界，比如用户域、订单域、支付域
  4. 按团队拆分：Conway 定律告诉我们，系统架构会趋向于组织结构

服务间通信方式的选择也很关键：REST 简单通用，gRPC 高性能适合内部通信，消息队列（Kafka/RabbitMQ）适合异步解耦，GraphQL 适合前端灵活查询。

服务注册与发现

服务多了之后，手动维护地址列表不现实。服务注册发现就是解决这个问题的：服务启动时把自己注册到注册中心（Consul、etcd、Nacos），其他服务通过注册中心发现目标地址。客户端负载均衡配合健康检查，自动剔除不健康实例。

API 网关

微服务对外暴露统一入口。网关承担的职责包括：路由转发、认证鉴权、限流、协议转换、日志聚合。常见方案有 Kong、Envoy、Go 自研网关等。好处是客户端不需要知道后面有多少个服务，也避免了跨域和安全策略分散的问题。

熔断、限流与降级

这三个是微服务稳定性的三板斧，面试也经常考：

限流控制请求速率，常见算法有四种：

  • 固定窗口计数器：实现简单，但有边界突发问题
  • 滑动窗口：解决边界突发，实现略复杂
  • 漏桶算法：固定速率处理，平滑流量但无法应对突发
  • 令牌桶算法：固定速率生成令牌，允许一定程度的突发（桶中积累的令牌）

实际项目中 gRPC 拦截器用令牌桶限制单用户 QPS，Redis + Lua 脚本做分布式限流是比较常见的做法。

熔断的思路类似保险丝：当某个下游服务的错误率超过阈值，自动切断调用，快速失败，等一段时间后再尝试恢复（半开状态探测）。防止一个慢服务拖垮整个系统。

降级是主动放弃非核心功能来保核心链路。比如大促期间关闭评论功能，把资源让给下单和支付。

链路追踪

一个请求可能经过五六个服务，出了问题怎么定位？分布式链路追踪的思路是给每个请求分配一个全局唯一的 traceID，在服务间透传，每个服务记录自己的 span（操作名、耗时、状态）。最终在 Jaeger 或 Zipkin 的 UI 里就能看到完整的调用链路和每段耗时。

Rinne-IM 的做法是客户端生成 traceID 放进 gRPC Metadata，服务端拦截器提取后注入 context，下游的 DB 查询、Redis 操作、Kafka 发送都自动携带这个 traceID。配合结构化日志（slog JSON 输出），排查延迟瓶颈非常高效。

分析：什么时候不该用微服务？

面试不能只说好处，面试官更想听你的判断力。以下场景建议不要上微服务：

  • 团队不到 10 人，项目处于 MVP 阶段——运维成本会吃掉开发效率
  • 业务边界不清晰——拆错了比不拆更痛苦
  • 没有基础设施支撑——没有 CI/CD、没有容器编排、没有监控体系，微服务就是给自己挖坑
  • 数据一致性要求极高——分布式事务的代价远比想象中高

Martin Fowler 提过一个建议：先做单体，等团队规模和业务复杂度到了需要拆分的时候，再逐步拆。这就是所谓的「单体优先（Monolith First）」策略。

知识点总结

概念一句话
单体架构简单直接，适合小团队和早期项目
微服务独立部署和扩展，但运维复杂度高
模块化单体逻辑拆分、物理合并，务实的中间路线
DDD 限界上下文服务拆分的理论依据
服务注册发现Consul/etcd/Nacos，解决服务地址管理
API 网关统一入口，路由/认证/限流
限流令牌桶最常用，控制请求速率
熔断快速失败，防止级联故障
降级牺牲非核心功能保核心链路
链路追踪traceID 透传 + span 记录，Jaeger/Zipkin

相关知识扩展

Service Mesh（服务网格）

当服务数量多到一定程度，每个服务都要写熔断、限流、链路追踪的代码，太累了。Service Mesh 把这些横切关注点下沉到基础设施层：每个服务旁边挂一个 Sidecar Proxy（数据平面），由控制平面统一管理配置、路由、负载均衡和熔断降级。主流实现是 Istio 和 Linkerd。好处是业务代码完全不需要关心服务治理逻辑，缺点是引入了一层额外的复杂度和性能开销。

Serverless

比微服务更极端的抽象——连服务都不需要管了，直接写函数。云厂商（AWS Lambda、阿里云函数计算）负责运行、扩缩容和计费。适合事件驱动、突发流量的场景，比如图片处理、定时任务。但冷启动延迟和厂商锁定是目前的主要限制。

学习路线与建议

  1. 先扎实单体：把分层架构（Controller - Service - Repository）和依赖注入搞清楚，这是所有架构的基础
  2. 理解 DDD：不需要一上来就全套 DDD，但限界上下文、聚合根、领域事件这些概念要知道
  3. 动手拆一次：拿自己的项目试试按业务域拆分，体会拆分的边界感
  4. 学一个服务框架：go-zero、go-micro 或者 Kratos，了解服务注册发现、熔断限流的开箱即用方案
  5. 了解 Service Mesh：Istio + Envoy 是趋势，至少要知道 Sidecar 模式的工作原理
  6. 监控先行：Prometheus + Grafana + Jaeger，可观测性是微服务的前提而不是锦上添花

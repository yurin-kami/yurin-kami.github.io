## 前情提要

在单机数据库里，事务靠 ACID 就能搞定。但系统一旦拆成微服务，一个业务流程往往要跨多个服务、多个数据库——这时候本地事务就不够用了，我们需要**分布式事务**来保证数据一致性。

这篇笔记整理自面试中最高频的分布式事务问题：四种主流方案分别是什么？各自适用什么场景？面试时该怎么组织回答？

## 问题

> 分布式环境下，一个操作涉及多个服务节点，如何保证要么全部成功，要么全部回滚？常见方案有哪些，它们的取舍是什么？

## 回答

### 方案一：两阶段提交（2PC）

2PC 是最经典的分布式事务协议，思路很直接——先问大家"准备好了没"，再统一发指令。

**阶段 1（Prepare）**：协调者向所有参与者发送 Prepare 请求。参与者执行事务操作但不提交，写 redo/undo 日志后返回 Yes 或 No。

**阶段 2（Commit/Rollback）**：如果所有参与者都返回 Yes，协调者发送 Commit；只要有一个返回 No，就发送 Rollback。

2PC 的优点是概念清晰，能保证强一致性。但缺点也很明显：

- **同步阻塞**：Prepare 阶段所有参与者都持有锁，互相等待，吞吐量很低。
- **单点故障**：协调者挂了，参与者只能一直阻塞等待，没有自愈能力。
- **数据不一致风险**：Commit 阶段如果部分参与者收到 Commit、部分没收到，数据就不一致了。

实际生产中很少直接用 2PC，但它是一切后续方案的思想起点。

### 方案二：TCC（Try-Confirm-Cancel）

TCC 把事务逻辑搬到了业务层，每个操作都要实现三个接口：

- **Try**：预留资源。比如下单时冻结库存 `frozen += 1`，但不真正扣减。
- **Confirm**：确认提交。真正扣库存 `stock -= 1, frozen -= 1`。
- **Cancel**：取消释放。解冻库存 `frozen -= 1`。

```plain
用户下单 -> Try(冻结库存) -> Try(冻结余额)
          |                        |
          v                        v
     全部成功? ──Yes──> Confirm(扣库存) -> Confirm(扣余额)
          |
          No
          |
          v
     Cancel(解冻库存) -> Cancel(解冻余额)
```

TCC 的核心优势是**不依赖数据库层面的事务**，性能好，适合高并发场景（电商、支付）。代价是业务侵入性强——每个服务都得写三套逻辑，开发成本高，而且 Confirm/Cancel 必须保证幂等。

### 方案三：Saga 模式

Saga 把一个大事务拆成一连串本地事务，每个本地事务都有对应的补偿操作。如果某一步失败，就逆序执行已完成步骤的补偿。

```plain
T1 -> T2 -> T3 -> T4   (正向执行)
C1 <- C2 <- C3         (T4 失败，逆序补偿)
```

Saga 有两种实现风格：

**编排式（Choreography）**：没有中心协调者，每个服务完成本地事务后发事件，下一个服务监听事件并执行。优点是解耦，缺点是流程一复杂就很难追踪。

**协调式（Orchestration）**：有一个中心协调器按顺序调用各个服务，失败时负责触发补偿。流程清晰，但协调器本身需要保证高可用。

Saga 适合长事务场景（比如订单履约、物流），但它的隔离性比较弱——中间状态对外可见，可能出现"脏读"。

### 方案四：本地消息表 + 定时补偿

这是最"接地气"的方案。核心思路：把"发消息"和"写业务数据"放在同一个本地事务里，靠消息队列 + 轮询来实现最终一致性。

```plain
BEGIN TRANSACTION
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;
  INSERT INTO outbox_messages (id, payload, status) VALUES (uuid, '...', 'pending');
COMMIT

-- 后台定时任务
SELECT * FROM outbox_messages WHERE status = 'pending';
  -> 发送到 MQ
  -> UPDATE outbox_messages SET status = 'sent';
```

优点是方案简单、不依赖特殊中间件、业务侵入小。缺点是只适用于对实时一致性要求不高的场景，且需要消费端做好幂等处理。

### 四种方案对比

| 维度 | 2PC | TCC | Saga | 本地消息表 |
|------|-----|-----|------|-----------|
| 一致性 | 强一致 | 最终一致 | 最终一致 | 最终一致 |
| 性能 | 低 | 高 | 中 | 中 |
| 业务侵入 | 低 | 高（三个接口） | 中（补偿逻辑） | 低 |
| 隔离性 | 有 | 有（预留资源） | 弱 | 无 |
| 实现复杂度 | 中 | 高 | 中 | 低 |
| 典型场景 | 金融核心 | 电商/支付 | 长流程业务 | 通知/异步场景 |

## 分析：CAP 视角下的一致性选择

回到 CAP 理论：分布式系统必须在 P（分区容错）的前提下，在 C（一致性）和 A（可用性）之间做取舍。

- **2PC 偏向 CP**：优先保证一致性，网络分区时宁可阻塞也不返回脏数据。
- **TCC / Saga / 本地消息表偏向 AP**：优先保证可用性，允许短暂的不一致，靠补偿机制达到最终一致。

这就引出了 **BASE 理论**——Basically Available（基本可用）、Soft State（软状态）、Eventually Consistent（最终一致性）。BASE 本质上是对 CAP 中 AP 方向的工程化落地：承认系统会存在中间状态，但只要最终能收敛到一致就行。

大多数互联网业务并不需要银行级别的强一致性，最终一致性 + 补偿机制在性能和可用性之间取得了更好的平衡。

## 知识点总结

1. **2PC** 是理论基石，强一致但性能差，生产中很少裸用。
2. **TCC** 性能好但开发成本高，适合对一致性和性能都有要求的金融/电商场景。
3. **Saga** 适合长事务、多步骤流程，但隔离性弱，需要容忍中间状态。
4. **本地消息表** 是最轻量的方案，适合异步通知类场景，搭配 MQ 使用效果最好。
5. 选型的核心判断标准：**一致性要求有多强？业务能不能接受中间状态？开发成本能承受多少？**

## 相关知识扩展

### Seata 框架

阿里巴巴开源的 Seata 是目前 Java 生态最主流的分布式事务框架，它把上述方案都做了封装：

- **AT 模式**：改良版 2PC，对业务无侵入，自动生成回滚 SQL。
- **TCC 模式**：业务自定义 Try/Confirm/Cancel。
- **Saga 模式**：支持状态机编排长事务。
- **XA 模式**：基于数据库 XA 协议的强一致方案。

如果用 Java 技术栈，Seata 基本是分布式事务的首选方案。Go 生态可以关注 DTM 等开源项目。

### 最终一致性 vs 强一致性

- **强一致性**：写完成后所有读立刻看到最新值。代价是高延迟、低可用。典型实现：2PC、Paxos、Raft。
- **最终一致性**：允许短暂不一致，经过一段时间后数据收敛。代价是业务需要处理中间状态。典型实现：TCC、Saga、消息队列。

实际工程中，80% 以上的场景用最终一致性就够了。面试时如果被追问"你们用的哪种"，建议结合具体业务说清楚选择理由。

## 学习路线与建议

1. **先理解 CAP 和 BASE**，搞清楚一致性和可用性的取舍关系。
2. **从 2PC 学起**，理解同步阻塞的根因，再推导为什么需要后续方案。
3. **手写一个 TCC demo**（哪怕只是伪代码），体会 Try/Confirm/Cancel 的语义。
4. **读 Saga 相关论文**（Hector Garcia-Molina 1987 年的原始论文），理解编排和协调的区别。
5. **跑一下 Seata 或 DTM 的样例项目**，感受框架是怎么把这些理论落地的。
6. **面试表达建议**：先总述四种方案，再挑一个最熟悉的深入展开，最后用 CAP/BASE 做总结收尾。

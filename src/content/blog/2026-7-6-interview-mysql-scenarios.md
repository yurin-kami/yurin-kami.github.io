# MySQL 面经与场景题：慢查询、分页、主从、分库分表该怎么答

如果说八股题考的是“你会不会背”，那场景题考的就是：

> 你能不能把原理落到排障、优化和取舍上。

这篇文章专门整理我检索到的主流简中 MySQL 面经里反复出现的开放题、追问题和场景题，尽量把回答结构做成“面试里能直接开口”的版本。

## 一、场景题最稳的总答法

MySQL 场景题不要一上来就抛结论，更稳的套路是：

1. 先定义问题现象
2. 再说定位手段
3. 再说原因分类
4. 最后说优化方案和取舍

你可以记成一句话：

> 先定位，再分层，再优化，最后补风险。

## 二、面试官问：怎么定位慢查询

### 标准回答模板

我一般会先用监控工具或者慢查询日志确认是不是数据库问题，再拿到具体 SQL，用 `EXPLAIN` 看执行计划，确认是索引没命中、扫描行数过多、回表太多、排序分页不合理，还是数据量已经到了需要架构升级的阶段。

### 可以展开的定位路径

1. 看接口耗时是否明显上升
2. 用 APM / 链路监控定位到具体 SQL
3. 没有监控时看慢查询日志
4. 用 `EXPLAIN` 和 `SHOW PROFILE` 之类工具分析
5. 判断是 SQL 问题、索引问题、表结构问题还是架构问题

### 常见加分点

- 会主动提到 `slow_query_log`
- 会区分“慢 SQL”与“整体资源瓶颈”
- 会说扫描行数和返回行数要同时看

## 三、面试官问：这条 SQL 很慢，你怎么分析

### 面试回答模板

我会先看执行计划，重点看是否走了预期索引、扫描了多少行、有没有回表、有没有 `Using filesort` 或 `Using temporary`。如果索引本身没问题，再看 SQL 写法是否导致索引失效，比如函数、隐式类型转换、左模糊、深分页。如果单条 SQL 已经优化到位但数据量还是太大，就要考虑归档、冷热分离、读写分离甚至分库分表。

### 常见原因分类

#### 1. 索引没走上

典型原因：

- 联合索引不满足最左前缀
- 函数包裹索引列
- 字段类型不匹配
- `OR` 条件导致优化器放弃索引

#### 2. 虽然走索引，但还是慢

可能是：

- 回表太多
- 范围太大
- 选择性差
- 排序或分组没走索引

#### 3. SQL 写法天然不友好

例如：

- 深分页
- 大表 Join
- 聚合过重
- 查大字段

## 四、面试官问：深分页怎么优化

### 常见错误答法

“加个索引就好了。”

这通常不够，因为深分页的核心问题不是有没有索引，而是：

> 前面的很多行仍然要被扫描、跳过。

### 更稳的答法

1. 优先改成游标分页 / 基于主键或时间的 seek 分页
2. 如果业务必须用页码分页，可以先用覆盖索引拿主键，再回表
3. 对历史数据多、翻页特别深的场景，考虑限制可翻页深度

### 例子

```sql
-- 直接深分页，代价高
SELECT * FROM orders ORDER BY id LIMIT 1000000, 20;

-- 先查主键，再回表
SELECT * FROM orders
WHERE id IN (
  SELECT id FROM orders ORDER BY id LIMIT 1000000, 20
);
```

但面试里要补一句：

> 真正更好的方案通常是游标翻页，因为它更符合大流量业务的访问模式。

## 五、面试官问：为什么建了索引还是不生效

### 回答框架

我会优先从索引失效场景看，再看优化器是否判断全表扫描更便宜。

### 高频场景

- `WHERE DATE(create_time) = '2026-07-06'`
- `phone` 是字符串，却用数字去查
- `LIKE '%abc'`
- 联合索引跳列使用
- 表太小，优化器认为全表扫成本更低

### 加分表达

> 索引不是“建了就一定用”，优化器会根据代价模型决定执行计划，所以面试里要强调“验证实际执行计划”，而不是只停留在理论上。

## 六、面试官问：项目里遇到死锁怎么办

### 回答模板

如果项目里出现死锁，我会先通过 `SHOW ENGINE INNODB STATUS` 看最近的死锁信息，确认是哪些事务、哪些 SQL、哪些索引记录互相等待。然后再从访问顺序、事务范围、索引命中和隔离级别四个方向去收敛。

### 常见原因

1. 两个事务加锁顺序不一致
2. 没走索引导致锁范围扩大
3. 事务太长，锁持有时间过久
4. RR 下间隙锁 / 临键锁带来额外冲突

### 常见优化

- 统一访问顺序
- 缩短事务
- 补索引，减少锁范围
- 热点更新改成更轻量的乐观锁

## 七、面试官问：你怎么解决主从延迟

这是很典型的“你做没做过线上系统”的问题。

### 标准答法

主从延迟本质上是从库消费 binlog 跟不上主库写入速度，所以要先分清是写入太快、从库执行能力不足，还是大事务、DDL、热点更新导致复制堆积。处理上一般分成三层：先定位延迟来源，再做复制链路优化，最后在业务层做一致性兜底。

### 常见原因

- 大事务一次性写太多
- 从库资源不足
- DDL 或批量更新阻塞复制
- 单线程复制能力不足

### 常见解法

- 拆小事务
- 提升从库资源
- 使用并行复制能力
- 热点业务写后读强制走主库
- 对缓存和读路由做一致性兜底

### 加分点

> 面试时最好主动说“读写分离会引入延迟一致性问题，所以不是所有读都能无脑走从库”。

## 八、面试官问：什么时候考虑分库分表

### 不推荐的答法

“单表一大就分库分表。”

### 更稳的答法

只有当单机容量、单表数据量、单机写入能力或者热点写入已经成为瓶颈，并且常规 SQL/索引/缓存/读写分离都无法解决时，才会进入分库分表阶段。

### 要先做哪些前置动作

- SQL 优化
- 索引优化
- 归档历史数据
- 读写分离
- 缓存前移

### 分库分表要补的代价

- 跨库 Join 难
- 跨库聚合难
- 分页复杂
- 分布式事务复杂
- 运维链路更长

### 面试答题模板

> 分库分表本质上是“用复杂度换容量和吞吐”，所以我会先看是不是已经到了单机瓶颈，再选择按用户、按时间还是按业务维度拆分，同时提前考虑全局主键、路由规则、跨库查询和迁移方案。

## 九、面试官问：库存扣减你会用什么方案

这种题很容易从 MySQL 一路追到缓存、分布式锁和幂等。

### 常见答法

#### 方案 1：悲观锁

```sql
SELECT stock FROM goods WHERE id = 1 FOR UPDATE;
UPDATE goods SET stock = stock - 1 WHERE id = 1;
```

优点：

- 逻辑简单
- 强一致性直观

缺点：

- 热点高并发下锁竞争重

#### 方案 2：乐观锁

```sql
UPDATE goods
SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = ?;
```

优点：

- 冲突少时吞吐更高

缺点：

- 冲突高时重试多

### 更稳的面试表达

> 如果并发量不大、强一致性优先，可以先用数据库事务加悲观锁；如果冲突可控、更追求吞吐，可以用版本号乐观锁；如果已经是秒杀级流量，通常要再往缓存预扣、异步削峰和最终一致性方向升级。

## 十、面试官问：为什么订单查询突然变慢

这个问题很常见，因为它能串起索引、慢查询、分页、锁和架构。

### 推荐回答顺序

1. 先确认是单条 SQL 慢还是整体链路慢
2. 看慢日志和执行计划
3. 判断是不是索引失效
4. 判断是不是数据量膨胀、深分页、排序、Join 导致
5. 判断是不是锁等待或主从延迟造成“看起来像慢”
6. 最后给出短期优化和长期方案

### 短期优化

- 补索引
- 改 SQL
- 限制深分页
- 减少返回字段

### 长期优化

- 数据归档
- 读写分离
- 缓存前置
- 分库分表

## 十一、面试官问：数据库和缓存怎么配合

虽然这题常被归到 Redis，但在 MySQL 面经里也很常出现。

### 可以怎么答

1. 热点数据优先走缓存，降低 MySQL 读压力
2. MySQL 仍然是最终真实数据源
3. 更新策略常见是先更新 DB，再删缓存
4. 需要关注缓存穿透、击穿、雪崩和双写一致性

### 加分点

> 数据库和缓存协同的核心不是“有没有缓存”，而是“回源链路能不能扛住，数据一致性要求是什么，热点怎么治理”。

## 十二、真实面经里常见的追问方式

很多 MySQL 面经不是直接问名词，而是这样问：

- 为什么加了联合索引，查询还是慢？
- 深分页你怎么处理？
- 主从复制延迟导致用户下单后查不到数据怎么办？
- 读写分离之后一致性怎么保证？
- 你们项目为什么没有做分库分表？
- 订单库存扣减为什么没用分布式锁？

这些题共同特点是：

> 面试官想看的是你的工程判断，而不是你能不能背出概念定义。

所以建议每道题都按“现象 -> 定位 -> 方案 -> 取舍”答。

| 场景 | 推荐答题关键词 |

| 慢查询定位 | 监控、慢日志、EXPLAIN、扫描行数 |

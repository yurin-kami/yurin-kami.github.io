# 面试笔记：MySQL InnoDB 为什么用 B+ 树做索引

> 准备面试时被"为什么不用红黑树"问到哑口无言，于是把 B+ 树索引从结构到实战彻底梳理了一遍。这篇文章只聚焦一个核心问题：InnoDB 的索引为什么长成这个样子，以及面试官会怎么追问。

### 前情提要

索引是 MySQL 面试中出场率最高的知识点，没有之一。几乎每一轮面试都会问：你用的是什么索引、为什么选 B+ 树、联合索引怎么走、什么时候会失效。我之前背过"叶子节点用链表连接"这种标准答案，但面试官一旦追问"那跳表不行吗"、"覆盖索引和普通索引有什么区别"，就只能支支吾吾。

后来我把 B+ 树相关的知识从数据结构层面到 SQL 优化层面做了一次完整的串联，发现这些问题其实是同一条逻辑链上的不同环节。把这条链理清，面试时不管怎么追问都能接住。

### 问题

面试中关于 B+ 树索引的常见问法：

- "InnoDB 为什么用 B+ 树做索引，而不是 Hash、红黑树或者跳表？"
- "聚簇索引和非聚簇索引有什么区别？什么是回表？"
- "什么是覆盖索引？什么是最左前缀原则？"
- "索引在什么情况下会失效？"
- "索引下推（ICP）是什么？"

这些问题看似独立，其实都围绕一个核心：**B+ 树的结构决定了 InnoDB 索引的全部行为**。

### 回答

**B+ 树的结构**

B+ 树是一棵平衡多路搜索树。核心特征：非叶子节点只存键值不存数据，叶子节点存储数据指针，叶子节点之间用双向链表连接。InnoDB 默认每个页 16KB，假设主键为 `BIGINT`（8 字节），加上指针开销，一个非叶子节点大约能存 1200 个键。这意味着：

- 2 层 B+ 树可索引约 144 万条数据
- 3 层可索引约 17 亿条数据

千万级数据的表，树高只有 3 层，查询最多 3 次磁盘 I/O。

```
          [10 | 20]
         /    |    \
    [1,5]  [10,15]  [20,25]
      |       |        |
    data    data     data
   ←──── 叶子节点链表 ────→
```

**为什么不用其他数据结构？**

| 数据结构 | 等值查询 | 范围查询 | 树高（千万级） | 磁盘 I/O |
|----------|---------|---------|---------------|---------|
| Hash 表 | O(1) | 不支持 | - | 1 次（但不支持范围） |
| 红黑树 | O(log N) | 支持 | ~24 层 | 24 次，不可接受 |
| 跳表 | O(log N) | 支持 | 概率性，最坏退化 | 不稳定 |
| B 树 | O(log N) | 支持 | 比 B+ 树高 | 每个节点存数据，扇出小 |
| **B+ 树** | **O(log N)** | **支持** | **3 层** | **3 次** |

Hash 等值最快但完全不支持范围查询和排序；红黑树是二叉树，千万级数据树高约 24 层，每层一次 I/O；跳表是概率平衡结构，最坏情况会退化成链表；B 树每个节点都存数据，导致单个页能存的键值更少，树更高。B+ 树在"矮"和"范围查询"两个维度上同时做到了最优。

**聚簇索引 vs 非聚簇索引**

InnoDB 的主键索引是聚簇索引：数据行直接存储在 B+ 树的叶子节点上，数据和索引物理上在一起。每张表只能有一个聚簇索引。

二级索引（非聚簇索引）的叶子节点存储的不是数据行，而是主键值。通过二级索引查询时，先找到主键，再到聚簇索引中查找完整数据行，这个过程叫**回表**。

```
聚簇索引（主键）：          二级索引（name）：
+-----+-------+-----+      +-----+-----+
| PK  | name  | age |      |name | PK  |
+-----+-------+-----+      +-----+-----+
| 1   | Alice | 30  |      |Alice| 1   |
| 2   | Bob   | 25  |      |Bob  | 2   |
| 3   | Carol | 35  |      |Carol| 3   |
+-----+-------+-----+      +-----+-----+
```

**覆盖索引**

如果查询的字段恰好都在某个二级索引中，就不需要回表，这叫覆盖索引。`EXPLAIN` 中 `Extra` 列会显示 `Using index`。

```sql
-- 联合索引 (name, age)
CREATE INDEX idx_name_age ON users (name, age);

-- 覆盖索引：只需要扫描索引，不回表
SELECT name, age FROM users WHERE name = 'Alice';

-- 非覆盖索引：需要回表取 email 字段
SELECT name, email FROM users WHERE name = 'Alice';
```

**最左前缀原则**

联合索引 `(a, b, c)` 在 B+ 树中的排序规则是：先按 `a` 排序，`a` 相同再按 `b` 排序，`b` 相同再按 `c` 排序。因此查询时必须从最左列开始连续匹配：

```sql
-- 走索引
WHERE a = 1
WHERE a = 1 AND b = 2
WHERE a = 1 AND b = 2 AND c = 3

-- 不走索引
WHERE b = 2
WHERE c = 3
WHERE b = 2 AND c = 3
```

MySQL 5.6 引入了**索引下推（Index Condition Pushdown, ICP）**：对于联合索引中无法直接用于定位的列，存储引擎层会在遍历索引时提前过滤，减少回表次数。`EXPLAIN` 中显示为 `Using index condition`。

### 分析

面试官问 B+ 树，真正关心的是三件事：你是否理解底层结构、能否解释 SQL 行为、会不会做索引优化。

**常见索引失效场景**（面试高频追问）：

1. **对索引列使用函数或表达式**：`WHERE YEAR(create_time) = 2026` 导致全表扫描，应改为范围查询
2. **隐式类型转换**：`WHERE phone = 13800000000`，`phone` 是 `VARCHAR`，数字会触发转换
3. **`LIKE` 左模糊**：`WHERE name LIKE '%lice'` 无法利用 B+ 树的有序性
4. **`OR` 条件中有非索引列**：`WHERE indexed_col = 1 OR non_indexed_col = 2`
5. **`NOT IN` / `NOT EXISTS`**：在某些场景下优化器会放弃使用索引
6. **联合索引不满足最左前缀**：跳过第一列直接用后面的列查询

理解失效的本质很重要：所有失效都源于一个原因——**查询条件破坏了 B+ 树的有序性**，导致优化器认为全表扫描比走索引更快。

### 知识点总结

| 概念 | 一句话 |
|------|--------|
| B+ 树 | 非叶子只存键、叶子存数据、叶子链表连接，3 层索引 17 亿行 |
| 聚簇索引 | 数据和索引物理上在一起，InnoDB 主键即聚簇索引 |
| 二级索引 | 叶子存主键值，查询需要回表 |
| 覆盖索引 | 查询字段全在索引中，不需要回表 |
| 最左前缀 | 联合索引必须从最左列连续匹配 |
| 索引下推 | 存储引擎层提前过滤，减少回表 |
| 索引失效 | 函数、隐式转换、左模糊、OR、不满足最左前缀 |

### 相关知识扩展

**索引合并（Index Merge）**

当查询条件涉及多个单列索引时，MySQL 可能同时使用多个索引再合并结果。`EXPLAIN` 中 `type` 显示为 `index_merge`。有三种策略：`union`（取并集）、`intersection`（取交集）、`sort-union`（先排序再合并）。实践中，如果频繁触发索引合并，往往说明应该直接建联合索引。

**MySQL 8.0 隐藏列**

如果建表时没有显式定义主键，InnoDB 会自动添加一个 6 字节的隐藏列 `DB_ROW_ID` 作为聚簇索引。从 MySQL 8.0 开始，可以通过 `INFORMATION_SCHEMA.INNODB_COLUMNS` 查看这些隐藏列。这也解释了为什么"没有主键的表性能差"——隐藏列的生成和维护都有额外开销。

**MySQL 8.0 降序索引**

MySQL 8.0 之前，索引定义中的 `DESC` 被解析器接受但实际忽略（始终升序存储）。8.0 开始真正支持降序索引：

```sql
-- 降序索引，对 ORDER BY col DESC 的查询有显著优化
CREATE INDEX idx_created_desc ON orders (user_id, created_at DESC);

SELECT * FROM orders WHERE user_id = 1 ORDER BY created_at DESC LIMIT 10;
```

这对"查某用户最新订单"这类高频场景非常有用，避免了内存排序（`Using filesort`）。

### 学习路线与建议

1. **先理解数据结构**：手动画一棵 B+ 树的插入和分裂过程，搞清楚为什么 3 层能索引千万级数据。
2. **再做对比实验**：用 `EXPLAIN` 对比 Hash 索引（Memory 引擎）和 B+ 树索引在等值、范围查询下的执行计划差异。
3. **然后掌握 EXPLAIN**：重点看 `type`（`ref` > `range` > `index` > `ALL`）、`key`、`Extra`（`Using index` / `Using index condition` / `Using filesort`）三列。
4. **最后结合项目**：拿自己项目中的真实查询做优化，比如把回表查询改成覆盖索引、把左模糊改成前缀匹配。面试时能说出"我在 XX 项目中把查询从 200ms 优化到 5ms"，比背十遍八股文都管用。

建议的学习顺序：B+ 树结构 → 聚簇/二级索引 → EXPLAIN → 最左前缀与失效场景 → 覆盖索引与索引下推 → 联合索引设计。每一步都带着 SQL 去验证，而不是只停留在概念层面。

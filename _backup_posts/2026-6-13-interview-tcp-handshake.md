## 前情提要

最近在系统性地整理网络编程的面试高频题，TCP 的三次握手和四次挥手绝对是绕不开的经典。几乎所有涉及网络通信的面试都会问到：为什么建立连接要三次，断开连接却要四次？这篇文章就从原理出发，把这个问题彻底讲透。

## 面试问题

> "请描述 TCP 三次握手和四次挥手的过程，并解释为什么握手是三次而不是两次或四次，以及 TIME_WAIT 状态的作用。"

## 回答

### 三次握手

先看流程图：

```
Client                          Server
  |                               |
  |--- SYN (seq=x) ------------->|   第一次：客户端发起连接请求
  |                               |
  |<--- SYN+ACK (seq=y, ack=x+1)-|   第二次：服务器确认并发起自己的连接请求
  |                               |
  |--- ACK (ack=y+1) ----------->|   第三次：客户端确认服务器的连接请求
  |                               |
  |======= 连接建立 ===============|
```

**过程解读：**

1. **第一次握手**：客户端发送 SYN 报文，进入 `SYN_SENT` 状态。这一步是客户端在说："我要建连接，你听到了吗？"
2. **第二次握手**：服务器收到 SYN 后，回复 SYN+ACK 报文，进入 `SYN_RCVD` 状态。服务器在说："听到了，我也准备好了，你呢？"
3. **第三次握手**：客户端收到 SYN+ACK 后，发送 ACK 报文，双方进入 `ESTABLISHED` 状态。客户端说："好的，都确认了，开始通信吧。"

**为什么不是两次？**

如果只有两次握手，服务器发完 SYN+ACK 就认为连接已建立，但客户端可能根本没收到这个回复（网络丢包）。此时服务器会一直等待客户端发送数据，白白占用资源。更严重的是，如果客户端的一个延迟旧 SYN 到达服务器，服务器会误以为是新的连接请求，建立一个无效的连接——这就是"历史连接的初始化"问题。**三次握手的本质是确保双方都确认了对方的收发能力。**

**为什么不是四次？**

三次已经足够确认双方的收发能力。第四次握手不会带来任何额外的可靠性收益，只会增加延迟和资源开销。三次是数学上的最优解。

### 四次挥手

```
Client                          Server
  |                               |
  |--- FIN (seq=u) ------------->|   第一次：客户端请求断开
  |                               |
  |<--- ACK (ack=u+1) ----------|   第二次：服务器确认收到
  |                               |
  |        (服务器继续发送剩余数据)  |
  |                               |
  |<--- FIN (seq=w) -------------|   第三次：服务器也请求断开
  |                               |
  |--- ACK (ack=w+1) ----------->|   第四次：客户端确认，进入 TIME_WAIT
  |                               |
  |======= 连接关闭 ===============|
```

**过程解读：**

1. **第一次挥手**：客户端发送 FIN，进入 `FIN_WAIT_1`。"我没数据要发了。"
2. **第二次挥手**：服务器回复 ACK，进入 `CLOSE_WAIT`。"知道了，但我可能还有数据没发完。"
3. **第三次挥手**：服务器数据发送完毕，发送 FIN，进入 `LAST_ACK`。"我也没数据了，可以关了。"
4. **第四次挥手**：客户端回复 ACK，进入 `TIME_WAIT`，等待 2MSL 后彻底关闭。

**为什么挥手要四次而不是三次？**

核心原因是 TCP 是**全双工**通信。关闭连接需要两个方向各自独立关闭。服务器收到客户端的 FIN 时，可能还有数据没发送完，所以 ACK 和 FIN 不能合并成一个报文（不像握手时 SYN+ACK 可以合并）。这就导致了四次挥手。

### TIME_WAIT 的作用与 2MSL

客户端在发送最后一个 ACK 后进入 `TIME_WAIT` 状态，持续 `2MSL`（Maximum Segment Lifetime，最大报文生存时间，通常为 2 分钟，即等待 4 分钟）。

**为什么需要 TIME_WAIT？**

1. **确保最后一个 ACK 到达**：如果这个 ACK 丢失，服务器会重发 FIN，客户端需要在 TIME_WAIT 状态下能够接收并重传 ACK。
2. **等待网络中的残留报文消亡**：防止旧连接的报文被新连接误收。

**为什么是 2MSL？**

一个 MSL 是报文在网络中存活的最长时间。2MSL 保证了：一来一回两个方向上的残留报文都有足够时间过期。这是 RFC 793 规定的工程经验值。

### SYN Flood 攻击与防御

**攻击原理：** 攻击者伪造大量虚假源 IP，向服务器发送 SYN 报文。服务器为每个 SYN 分配资源并回复 SYN+ACK，但永远不会收到第三次握手的 ACK。大量"半连接"堆积，耗尽服务器的连接队列和内存。

**防御手段：**

- **SYN Cookie**：不在收到 SYN 时立刻分配资源，而是通过加密哈希计算序列号，在收到第三次握手的 ACK 后才真正建立连接。
- **限制半连接数量**：设置 `tcp_max_syn_backlog` 参数限制 SYN 队列大小。
- **缩短 SYN 超时时间**：快速释放无响应的半连接。
- **防火墙/IPS 过滤**：检测并丢弃异常的 SYN 流量。

## 分析

这道题的考察点不只是"记住流程"，而是理解**设计决策背后的原因**。面试官希望看到的是：

- 你能从"双方确认收发能力"这个角度解释三次握手，而不是死记硬背。
- 你能从"全双工独立关闭"的角度解释四次挥手，而不是简单说"因为要四次"。
- 你了解 TIME_WAIT 不是浪费，而是可靠性保证的一部分。
- 你能把理论和安全实践（SYN Flood）联系起来。

## 知识点总结

| 知识点 | 核心要点 |
|--------|---------|
| 三次握手 | 确认双方收发能力，防止历史连接，三次是最优解 |
| 四次挥手 | 全双工各方向独立关闭，FIN 和 ACK 不能合并 |
| TIME_WAIT | 持续 2MSL，保证最后 ACK 可达 + 残留报文消亡 |
| 2MSL | 一来一回的报文最大生存时间，RFC 793 规定 |
| SYN Flood | 伪造 SYN 耗尽半连接资源，用 SYN Cookie 防御 |
| TCP 可靠性 | 校验和、序列号、确认应答、超时重传、流量控制、拥塞控制 |

## 相关知识扩展

### TCP 拥塞控制的四个阶段

TCP 的可靠性不仅靠握手和挥手，还依赖拥塞控制：

1. **慢启动（Slow Start）**：连接建立初期，拥塞窗口从 1 个 MSS 开始，每收到一个 ACK 翻倍（指数增长），直到达到慢启动阈值 ssthresh。
2. **拥塞避免（Congestion Avoidance）**：窗口超过 ssthresh 后，每个 RTT 只增加 1 个 MSS（线性增长），谨慎探测网络容量。
3. **快重传（Fast Retransmit）**：收到 3 个重复 ACK 时，立即重传丢失报文，而不是等待超时。
4. **快恢复（Fast Recovery）**：快重传后，将 ssthresh 和拥塞窗口设为当前窗口的一半，然后进入拥塞避免阶段，而不是回到慢启动。

### TCP vs UDP 选型速查

| 维度 | TCP | UDP |
|------|-----|-----|
| 连接 | 面向连接 | 无连接 |
| 可靠性 | 可靠（有序、不丢、不重） | 不可靠 |
| 传输 | 字节流 | 数据报 |
| 拥塞控制 | 有 | 无 |
| 效率 | 较低 | 高 |
| 场景 | HTTP、文件传输、数据库 | 视频流、游戏、DNS、QUIC |

实际工程中，QUIC 协议（HTTP/3 的基础）正在用"UDP + 应用层可靠性"的方式取代部分 TCP 场景，值得持续关注。

## 学习路线与建议

1. **先读 RFC 793**：TCP 的原始规范，三次握手和四次挥手的权威定义。
2. **抓包实践**：用 Wireshark 或 `tcpdump` 抓一次真实的 TCP 连接，观察 SYN、ACK、FIN 报文的序列号变化，比看十遍书都有用。
3. **理解状态机**：画出 TCP 的完整状态转换图（11 个状态），面试中偶尔会追问 `CLOSE_WAIT` 和 `TIME_WAIT` 的区别。
4. **动手写 Socket**：用 C 或 Go 写一对 TCP Client/Server，体验 `bind`、`listen`、`accept`、`connect` 的调用顺序和阻塞行为。
5. **进阶阅读**：《TCP/IP 详解 卷1》（W. Richard Stevens）第 17-24 章是 TCP 部分的圣经级参考。

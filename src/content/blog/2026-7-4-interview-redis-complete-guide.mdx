# Redis 八股总集：一篇吃透简中高频面试题

这篇文章不是单纯堆概念，而是把我检索到的主流简中 Redis 面试题源做了一次去重整理，尽量还原出面试里最常见的提问链路：

- Redis 是什么，为什么快？
- 五大数据结构怎么选？
- 过期策略、淘汰策略怎么讲？
- 缓存穿透、击穿、雪崩怎么区分？
- RDB、AOF、混合持久化怎么选？
- 主从、哨兵、Cluster 分别解决什么问题？
- Redis 分布式锁为什么要配合 Lua？

如果你时间不多，可以先记住一句话：

> Redis 面试最核心的不是“背了多少名词”，而是你能不能把“场景、原理、取舍”三件事串起来。

## 一、Redis 是什么？为什么大家都爱问它？

### 标准答法

Redis 是一个基于内存的键值数据库，支持多种数据结构，常见用途包括缓存、计数器、排行榜、消息队列、分布式锁、会话共享等。  
它读写非常快，但本质上不是拿来完全替代关系型数据库的，而是用来承接热点读写和高并发场景。

### 面试追问：Redis 为什么快？

标准回答一般分成 5 点：

1. **纯内存访问**
   数据主要在内存里，避免了磁盘随机 I/O。

2. **单线程执行核心命令**
   核心命令执行路径简单，避免了多线程锁竞争和上下文切换开销。

3. **I/O 多路复用**
   Redis 用 `epoll` / `kqueue` 这一类机制处理大量连接，不会被单个连接阻塞。

4. **数据结构设计高效**
   Redis 不是只会存字符串，它针对不同场景设计了 Hash、ZSet、Bitmap、Stream 等结构。

5. **大多数命令时间复杂度低**
   常见 `GET`、`SET`、`HGET`、`INCR` 都是高频且低复杂度操作。

### 面试追问：Redis 不是单线程吗？Redis 6 为什么又说支持多线程？

这个问题很容易答糊。

更准确的说法是：

- **命令执行模型仍然以单线程为主**
- **Redis 6 引入的多线程主要用于网络 I/O、协议解析等阶段**
- **不是把核心数据结构的读写彻底改成并行执行**

所以面试里最好不要简单说“Redis 是单线程”或者“Redis 现在是多线程”，而是说：

> Redis 的核心命令执行路径仍然主要是单线程，这样可以减少锁竞争；Redis 6 之后把部分 I/O 工作并行化了，但核心数据读写并没有完全改成多线程执行。

## 二、Redis 常用数据结构怎么答？

### 1. String

最常用的数据类型，适合：

- 缓存普通字符串
- 缓存 JSON
- 计数器
- 验证码
- 分布式锁

典型命令：

```bash
SET user:1 '{"name":"kami"}'
INCR article:1001:view
SET lock:order:1 uuid NX EX 10
```

### 2. Hash

适合存对象字段，尤其是字段会被局部更新的场景。

适合：

- 用户信息
- 商品属性
- 购物车
- 配置项集合

典型命令：

```bash
HSET user:1001 name kami age 20 city Shanghai
HGET user:1001 name
HGETALL user:1001
```

### 3. List

有序、可重复，适合：

- 消息队列的简化版
- 最新动态列表
- 时间线
- 历史记录

典型命令：

```bash
LPUSH queue task1
BRPOP queue 0
LRANGE timeline 0 19
```

### 4. Set

无序、不重复，适合：

- 去重
- 标签系统
- 共同好友 / 共同关注
- 抽奖

典型命令：

```bash
SADD tags:user:1 redis golang cache
SISMEMBER tags:user:1 redis
SINTER follow:a follow:b
```

### 5. ZSet

带分数的有序集合，适合：

- 排行榜
- 延时队列
- 热度排序
- 带权重的 Feed 流

典型命令：

```bash
ZADD rank 100 user:a 95 user:b 88 user:c
ZREVRANGE rank 0 9 WITHSCORES
ZRANK rank user:b
```

### 高频追问：五大结构怎么选？

可以直接按这个思路答：

- 只存一个值，或者做计数器：`String`
- 存对象并支持字段级更新：`Hash`
- 需要保留插入顺序：`List`
- 需要去重或集合运算：`Set`
- 需要按分数排序：`ZSet`

### 高频追问：Redis 还有哪些特殊结构？

常见补充项：

- `Bitmap`：签到、布隆过滤器底层位图能力、在线状态统计
- `HyperLogLog`：基数统计，比如 UV
- `Geo`：附近的人、门店距离
- `Stream`：更像正式队列，支持消费者组、ACK、积压处理

## 三、为什么 Redis 不只考“会用”，还会考“底层”？

因为很多八股文都会往底层追一层：

- ZSet 为什么适合排行榜？
- 为什么跳表不用红黑树？
- 小对象为什么内存占用低？

面试里不一定要讲源码细节，但最好知道 Redis 的设计思想：

> 小数据量时用更紧凑的编码省内存，数据量大了再切换到更适合查询和更新的结构。

例如大家常背的这些关键词：

- Hash 小时会用紧凑编码，变大再切换到哈希表
- ZSet 小时会用紧凑编码，变大后常见地转为跳表 + 哈希表
- Set 全是整数且数量不大时可以用更省内存的整数集合

面试官真正想听到的是：

> Redis 的底层设计不是为了“炫技”，而是为了在内存占用和操作性能之间做平衡。

## 四、过期策略和淘汰策略怎么区分？

这是一个很高频的混淆点。

### 1. 过期策略

过期策略解决的是：

> 给某个 key 设置了 TTL，它到期后 Redis 什么时候删它？

常见答案：

- **惰性删除**：访问 key 时发现过期了再删
- **定期删除**：后台定期随机抽样检查过期 key 并清理

为什么不用“定时删除”？

因为每个 key 都单独维护定时器开销太大，Redis 不这么做。

### 2. 内存淘汰策略

淘汰策略解决的是：

> Redis 内存不够了，还要写新数据，这时删谁？

常见策略可以按两类记：

- **只在设置了过期时间的 key 里淘汰**
  - `volatile-lru`
  - `volatile-lfu`
  - `volatile-random`
  - `volatile-ttl`

- **在所有 key 里淘汰**
  - `allkeys-lru`
  - `allkeys-lfu`
  - `allkeys-random`

还有：

- `noeviction`：不淘汰，直接报错

### 面试怎么讲更稳？

你可以这样说：

> 过期策略是处理“该过期的 key 什么时候删除”，淘汰策略是处理“内存满了之后新写入怎么腾空间”。前者关注 TTL，后者关注 maxmemory 场景。

## 五、缓存穿透、击穿、雪崩怎么答才不乱？

这是 Redis 面试里的经典三连问。

### 1. 缓存穿透

**定义**：请求的数据根本不存在，缓存没有，数据库也没有，请求每次都打到数据库。

**典型场景**：

- 恶意请求不存在的 ID
- 业务参数校验不严

**解决方案**：

- 缓存空值
- 布隆过滤器
- 接口层参数校验

### 2. 缓存击穿

**定义**：某个热点 key 过期瞬间，海量请求同时打到数据库。

**典型场景**：

- 热门商品详情
- 热搜内容
- 秒杀活动配置

**解决方案**：

- 互斥锁 / 分布式锁
- 热点 key 逻辑过期
- 后台预热刷新

### 3. 缓存雪崩

**定义**：大量 key 同时过期，或者 Redis 整体不可用，导致流量成批压到数据库。

**解决方案**：

- 过期时间加随机值
- 多级缓存
- 限流、熔断、降级
- Redis 高可用部署

### 一句话区分

- **穿透**：查不存在
- **击穿**：热点 key 过期
- **雪崩**：大量 key 同时挂，或者 Redis 挂

### 高频追问：这三个问题本质上在防什么？

本质上都是在防：

> 缓存失效后，数据库被并发流量直接冲垮。

所以你不必把它们背成三个孤立名词，应该把它们理解成三种不同的缓存失效场景。

## 六、缓存设计八股怎么答？

这一部分最稳的答法，不是只背几个名词，而是按“目标、对象、Key、TTL、更新、热点、大 Key、多级缓存”这一条链路来讲。

### 1. 为什么要加缓存？

- 抗住高并发读请求，降低数据库压力。
- 缩短访问链路，降低接口响应时间。
- 把热点数据前移，提升系统整体吞吐。

### 2. 缓存什么数据？

优先缓存：

- 读多写少的数据
- 热点明显的数据
- 计算代价高、聚合代价高的数据
- 能接受短暂最终一致的数据

### 3. Key 怎么设计？

Key 设计要做到：

- 可读
- 唯一
- 可治理

常见模板：

```text
业务名:对象名:主键[:维度]
```

### 4. TTL 怎么设计？

TTL 要和业务时效性绑定，不建议拍脑袋设置。高频加分点是：

- 给 TTL 加随机值，避免同一批 key 同时过期。
- 热点 key 不要只依赖自然过期，最好配合后台刷新。

### 5. 更新策略怎么答？

最常见的是 Cache Aside：

1. 读时未命中，再查数据库并回填缓存。
2. 写时先更新数据库，再删除缓存。

原因是“删除缓存”通常比“精确更新缓存”更简单、更稳。

### 6. 热点 Key 怎么处理？

常见手段：

- 永不过期加后台异步刷新
- 逻辑过期
- 互斥锁限制并发回源
- 本地缓存加 Redis 做多级缓存

### 7. 大 Key 怎么处理？

大 Key 会带来传输慢、删除慢、迁移慢和主从同步放大等问题。常见解法是拆 Key、按字段或分页拆分、定期扫描治理。

### 8. 多级缓存怎么讲？

典型顺序可以是：客户端缓存、CDN、网关层缓存、应用本地缓存、Redis、数据库。

关键不只是把层次背出来，而是说明：越靠前命中越快，但一致性治理也越复杂。

### 9. 设计题标准回答模板

如果面试官让你设计缓存方案，可以按这个顺序回答：

1. 明确缓存目标。
2. 圈定缓存对象。
3. 设计 Key、TTL 和容量边界。
4. 选择读写策略。
5. 补齐穿透、击穿、雪崩、热点 Key、大 Key 等异常场景。
6. 再补监控指标，比如命中率、回源率、淘汰率和内存水位。
## 七、Redis 和数据库双写一致性怎么讲？

这是 Redis 面试中最容易从“缓存问题”一路追问到“系统设计”的点。

### 常见更新策略

最常见的是 **Cache Aside**：

1. 先更新数据库
2. 再删除缓存

为什么不是“先删缓存再更新数据库”？

因为那样会有更明显的并发窗口，容易把旧数据重新写回缓存。

### 为什么是“更新数据库 + 删除缓存”，而不是“更新数据库 + 更新缓存”？

因为缓存通常是结果性数据、聚合数据，更新缓存的逻辑更复杂，也更容易遗漏。  
相比之下，删除缓存更简单，下一次请求再从数据库回源构建新缓存。

### 仍然有没有不一致窗口？

有。

比如：

1. 线程 A 更新数据库
2. 线程 B 读缓存未命中，回源读到旧值
3. 线程 B 把旧值写回缓存
4. 线程 A 删除缓存

或者顺序稍微变化，也会出现短暂不一致。

### 常见兜底方案

- 延迟双删
- binlog + MQ / Canal 异步删缓存
- 给缓存设置较短过期时间
- 对强一致要求高的场景减少缓存依赖

面试里别把它答成“Redis 保证强一致”，更稳的表达是：

> 缓存和数据库通常只能做到最终一致性，关键是缩小不一致窗口，并根据业务重要性做取舍。

## 八、Redis 持久化怎么答？

### 1. RDB

RDB 是快照持久化，核心思想是在某个时间点把内存数据整体做快照保存到磁盘。

**优点**：

- 文件紧凑
- 适合备份
- 恢复速度快

**缺点**：

- 两次快照之间的数据可能丢失
- `fork` 子进程和大快照会带来额外开销

### 2. AOF

AOF 是追加日志持久化，把写命令追加到文件里，重启时重放命令恢复数据。

**优点**：

- 数据安全性通常更高
- 丢失窗口更小

**缺点**：

- 文件更大
- 恢复通常更慢
- 需要 AOF 重写控制文件体积

### 3. 混合持久化

Redis 4.0 之后支持混合持久化，常见理解是：

- 利用 RDB 提升恢复速度
- 利用 AOF 保证更好的数据完整性

### 高频追问：线上一般怎么选？

通用答法：

- 只关心恢复快、容灾备份：偏 `RDB`
- 更关心数据安全：偏 `AOF`
- 生产里常见是 **同时开启**，或者开启混合持久化

### 高频追问：RDB 的 `SAVE` 和 `BGSAVE` 区别？

- `SAVE`：同步执行，会阻塞主线程
- `BGSAVE`：后台子进程执行，线上更常用

### 高频追问：AOF 为什么还要重写？

因为 AOF 是命令追加式的，时间一长会很大。  
重写的目的不是简单压缩文件，而是用更少的命令表达当前数据集状态。

## 九、Redis 事务和 Lua 怎么答？

### 1. Redis 事务

Redis 事务主要靠：

- `MULTI`
- `EXEC`
- `DISCARD`
- `WATCH`

它的特点是：

- 可以把一组命令打包顺序执行
- 但它不像关系型数据库那样提供完整 ACID 语义
- Redis 不支持传统意义上的事务回滚

所以面试里不要说“Redis 事务和 MySQL 事务差不多”，这是大坑。

### 2. WATCH 的作用

`WATCH` 用于乐观锁控制。  
如果被监控的 key 在提交前被别人改了，事务提交会失败。

### 3. 为什么很多场景更喜欢 Lua？

因为 Lua 脚本可以把多条命令放到 Redis 里一次执行，天然具备原子性，避免多次网络往返。

常见场景：

- 分布式锁释放
- 秒杀扣库存
- 组合校验 + 更新

面试里的经典回答是：

> 事务解决的是“命令打包顺序执行”，Lua 更适合“把一段需要原子执行的业务逻辑封到 Redis 内部一次完成”。

## 十、Redis 分布式锁怎么答？

这是从缓存一路延伸到分布式系统的高频题。

### 最基本写法

```bash
SET lock:order:1001 uuid NX EX 10
```

含义：

- `NX`：key 不存在才加锁
- `EX 10`：10 秒后自动过期，避免死锁
- `uuid`：标识锁的持有者

### 为什么 value 不能写死？

因为释放锁时要判断“是不是我自己的锁”。

如果 value 写死，线程 A 锁过期后，线程 B 拿到新锁，这时线程 A 再 `DEL`，就可能把线程 B 的锁误删。

### 为什么删除锁要用 Lua？

因为“先比对 value，再删除 key”如果拆成两条命令，就不是原子操作。

正确思路是把“校验 + 删除”放进 Lua 脚本里一次执行。

### 常见追问

#### 1. 业务执行超过锁过期时间怎么办？

可能出现锁提前过期，其他线程进来并发执行。  
常见做法：

- 业务评估合理超时时间
- 使用看门狗续期机制
- 直接用成熟框架，比如 Redisson

#### 2. Redis 主从切换会不会让锁丢失？

会，这是分布式锁的经典风险点之一。  
比如主节点刚加锁，还没同步到从节点就宕机，从节点升级成主后，这把锁可能消失。

所以更稳的回答不是“Redis 分布式锁完美可靠”，而是：

> Redis 分布式锁适合大多数工程场景，但如果对一致性要求极高，需要额外评估主从切换、网络分区和时钟问题，必要时结合业务幂等、补偿机制，或者选择更合适的协调方案。

## 十一、主从、哨兵、Cluster 怎么答？

### 1. 主从复制

主节点负责写，从节点同步数据并可承接读流量。

解决的问题：

- 读写分离
- 数据副本
- 基础高可用能力

### 2. 主从同步分哪两种？

- **全量同步**
  首次同步或差异太大时，主节点生成 RDB 发给从节点，再补发送期间的增量命令。

- **增量同步**
  从节点断线重连时，如果主节点复制积压缓冲区里还有缺失数据，就只补缺失部分。

### 3. 哨兵 Sentinel

哨兵是在主从基础上增加自动故障发现和自动故障转移能力。

它主要做三件事：

- 监控主从节点
- 主节点故障时选新主
- 通知客户端新的主节点地址

### 4. Cluster

Cluster 解决的是：

- 单机容量上限
- 单主写入瓶颈
- 水平扩展问题

它通过 **哈希槽** 做分片。  
常见面试答案：

> Redis Cluster 把整个 key 空间拆成 16384 个槽，每个主节点负责一部分槽，客户端根据 key 计算槽位并路由到对应节点。

### 高频追问：为什么哨兵还不够，还要 Cluster？

因为哨兵解决的是 **高可用**，不是 **水平扩展**。  
哨兵模式下每个节点通常还是一整份数据，容量和写入瓶颈仍然在单主上。

### 高频追问：16384 个槽是干嘛的？

它不是随便选的数字，本质上是为了：

- 让分片映射稳定
- 让节点迁移和扩缩容更容易
- 控制集群元数据开销

### 高频追问：什么是 Hash Tag？

在 Cluster 下，多 key 操作要求尽量落到同一个槽。  
如果 key 写成：

```text
{user:1001}:name
{user:1001}:profile
```

那么 Redis 会用花括号里的内容参与槽计算，这样相关 key 可以落到同一个槽，便于多 key 操作。

## 十二、Redis 常见面试误区

### 误区 1：Redis 是单线程，所以并发不高

错。  
Redis 的高性能恰恰来自“单线程执行核心命令 + I/O 多路复用 + 内存访问快 + 数据结构高效”的组合。

### 误区 2：有了哨兵就等于分布式扩容

错。  
哨兵解决高可用，不解决数据分片和单机容量瓶颈。

### 误区 3：缓存和数据库一定能强一致

错。  
多数场景只能做到最终一致性，重点是缩小不一致窗口。

### 误区 4：Redis 分布式锁天然绝对安全

错。  
它有工程适用边界，需要结合超时、续期、主从复制、幂等、补偿一起看。

### 误区 5：把五种数据类型背下来就够了

不够。  
面试官更想看你是否能从“使用场景”讲到“为什么选它”，再讲到“可能踩什么坑”。

## 十三、Redis 面试速记版

如果你只想在面试前快速扫一遍，可以记住下面这张表。

| 模块 | 高频问题 | 关键回答 |
| --- | --- | --- |
| 基础 | Redis 为什么快 | 内存、单线程核心执行、I/O 多路复用、高效结构、低复杂度命令 |
| 数据结构 | 五大类型怎么选 | String 值、Hash 对象、List 顺序、Set 去重、ZSet 排序 |
| 过期与淘汰 | 两者区别 | 过期策略看 TTL，淘汰策略看内存满 |
| 缓存问题 | 穿透/击穿/雪崩 | 查不存在 / 热点过期 / 大量失效或 Redis 挂 |
| 持久化 | RDB vs AOF | RDB 恢复快，AOF 更安全，生产常组合 |
| 一致性 | 缓存双写 | 常见是更新 DB 后删缓存，只能追求最终一致 |
| 事务 | Redis 事务特点 | 有顺序执行，无传统回滚 |
| Lua | 为什么常用 | 原子执行复杂逻辑，减少网络往返 |
| 分布式锁 | 正确姿势 | `SET NX EX` + 唯一 value + Lua 解锁 |
| 高可用 | 主从/哨兵/集群 | 读写分离 / 自动故障转移 / 分片扩容 |
